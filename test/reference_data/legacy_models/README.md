# Legacy-driver golden capture (Stage 0)

Generated by `tools/capture_legacy_models.jl` at git SHA `8faf5f2516152a592c7cb3b375c0eb67009de55a` (dirty working tree), 2026-09-24 23:06:01.

**These goldens stay as the historical record.** `tools/capture_legacy_models.jl` and its
one-shot check, `test/test_legacy_fingerprints.jl`, were removed at Stage 5 of the config
consolidation (commit `ad57265` is where the capture tool last existed, for anyone who needs
to re-derive a fingerprint by hand). The live check that `build_model(load_config(...))`
still reproduces these values key-by-key is `test/test_config_equivalence.jl`, which reads
these `.toml`/`.hashes.toml` files directly and keeps using `test/config_fingerprint.jl`.

Each `<arm>.toml` is a fingerprint (`test/config_fingerprint.jl`) of the `ModelParameters`/`NestedModelParameters` the corresponding legacy driver (`tc/tc_params.jl`+`tc/tc_init.jl`, `benchmarks/ocean_rce.jl`, `benchmarks/ocean_warm_bubble.jl`) builds for that arm's environment. Each `<arm>.hashes.toml` (where present) is basename => SHA-256 of every initial-condition CSV and the reference-state `.ref` file that arm's own `init!` writes on a scratch grid. No integration timestep was run to produce any of this. These are the values a future `build_model(cfg)` replacement must reproduce key-by-key (plan §7 "Equivalence"/"IC bytes").
